## Evidence retention rules

For every run, retain:

- exact command line and exit code;
- wall-clock start and finish time;
- platform and architecture;
- redacted stdout/stderr or linked artifact path;
- test report or trace path when generated;
- screenshots for any manual confirmation associated with the command;
- rerun count and reason if the command was repeated.

Evidence must not retain:

- credential values;
- pairing codes or bearer tokens;
- viewer URLs with secrets;
- production account identifiers;
- unredacted local home-directory paths unless the path itself is the subject of the test.

## Failure classification

| Class | Meaning | Required next action |
|---|---|---|
| Product defect | The code under test behaves incorrectly | File a P0/P1/P2 defect, preserve first-failure evidence, rerun the narrowest owning suite after a fix |
| Test defect | The product is correct but the test or fixture is wrong | Preserve the failing test evidence, fix the test, rerun the narrow suite and at least one neighboring suite |
| Environment defect | Toolchain, runner, VM, permission, or network issue invalidated the run | Record the exact missing prerequisite and mark blocked; do not count as pass |
| Provider variation | External system changed within the supported bounds | Capture it explicitly and evaluate whether Helmryth still fails closed and remains usable |
| Flake | Same code and environment produce inconsistent outcomes | Treat as failing until either root-caused or quarantined with owner, reason, and expiry |

## Rerun discipline

- Re-running a failing command is allowed only after the first-failure evidence is captured.
- A rerun after code or fixture changes must include the narrow failing command, the domain suite, and the next broader gate affected by the change.
- A flaky pass is not a pass. The execution report must record the first failure and the final disposition.
