## Operators are persistent teammates

An operator keeps its own workstream, model, instructions, work folder, memory, connected capabilities, and workbench preference. Create separate operators when the role, access, or project context should differ.

- A coding operator attached to one repository
- A research operator with browser and document capabilities
- An operations operator with Gmail, Calendar, and Slack
- A local-model operator for private or offline work

## Runs are focused workstreams

Use **Run** when the work should have a clear beginning and result. Runs are easier to track than mixing every request into the operator's main workstream, and scheduled cadences create runs automatically.

## Crews and handoffs

Crews let multiple operators and people share context. Use a crew when several specialists need the same brief or should hand work to one another. A chief-of-staff pattern works well: one operator receives the request, delegates focused runs, and summarizes the result.

## Delegation

Delegation asks another operator to handle a bounded subworkstream. The delegated run keeps its own activity and returns a result to the originating workstream. Give each delegate a narrow outcome and avoid assigning two operators ownership of the same files.

| Need | Use |
|---|---|
| Ongoing relationship and memory | Operator |
| One deliverable with a status | Run |
| Several participants sharing context | Crew |
| A specialist handling one branch of work | Delegation |
| Repeated work at a known time | Cadence |
